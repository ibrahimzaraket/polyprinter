How It Works

A map of the actual code, function by function — what runs, in what order, and exactly how a decision gets made. Everything below describes what's really in the repo today, not a plan. Terms in ? style are explained on the Definitions tab.

Where things stand right now: Phase 0 (spine), Phase 1 (Scout), Phase 2 (Mirror, polling/paper), and Phase 3 (Mandates, via an LLM over OpenRouter) are all live. Mandates are real, judged against real dossier numbers, and stored in full — but so far every mandate issued has come back SKIP. That's the model's actual judgment on the current watchlist so far (reasons cited include low hold-to-resolution rates and heavy profit concentration on a handful of trades), not a wiring bug — see the Mandates section below for what a real one looks like. Until a FOLLOW verdict actually gets issued, Mirror's entries still resolve to SKIP/MANDATE_NOT_FOLLOW (or occasionally still NO_MANDATE, for a trader not yet evaluated) — the mechanism is proven, real capital is still nowhere near being risked. Phase 4 (on-chain event detection) is under way: it watches the same traders directly on Polygon and logs what it sees for comparison, but it does not drive any decision yet — polling stays the only path that opens/closes anything until a 72-hour clean-diff window proves the two agree (PRD §7's Phase 4 exit criterion). See the Mirror — event detection section below.

The three services, at a glance

Three independent processes, one shared SQLite file (data/polyprinter.db, WAL mode) as the single source of truth. No service calls another directly — they only ever talk through the database. Each table has exactly one owner allowed to write it (enforced by convention, not by SQLite itself — see the invariants below); everyone else only reads.

Scout — discovers and scores traders

One full Scout run: pull the Polymarket leaderboard, fetch each candidate's trade history, compute a scored "dossier," and write one snapshot row per trader. Runs standalone — nothing here depends on Mirror or a mandate existing.

polyprinter/scout/discover.py— who counts as a candidate

Pulls the public Polymarket leaderboard across 4 time windows (day / week / month / all-time) × 2 orderings (by profit, by volume) — 8 calls total, unioned and de-duplicated by wallet address. Ordering by volume as well as profit is deliberate: selecting candidates only by realised profit is the exact survivorship bias the whole project exists to correct for (a trader can be #1 on the leaderboard purely from variance).

discover_candidates(client, per_window_limit=50)
Runs all 8 leaderboard calls, returns one de-duplicated list of Candidate (address, username, which window/ordering first found them, their volume and P&L at discovery time).
upsert_traders(conn, candidates)
Inserts any address not already in the traders table. Existing traders are left untouched — first_seen and discovery_source are set once, never overwritten.

Documented gap: the PRD also suggests sampling by resolved-position count, but no Polymarket endpoint ranks all users by that — verified against the live API, not implemented.

polyprinter/scout/dossier.py— the actual scoring: one candidate in, ~20 metrics out

For one trader address: fetches their open positions, closed (resolved) positions, and full trade activity from Polymarket, then computes every field that ends up as one row in trader_snapshots.

compute_dossier(client, address)
The main function. Fetches positions/closed-positions/activity, then computes performance (raw ROI, win rate, avg win/loss, profit concentration), copyability (hold-to-resolution rate, holding period, entry-price spread, sizing pattern), and liveness (trade counts, active flag). Returns one DossierMetrics object.
_percentile(values, pct)
Linear-interpolation percentile — used for the p10/median/p90 entry-price spread and the p90 holding period.
_fetch_all_closed_positions / _fetch_all_activity(client, address)
Pagination helpers. Bounded, not exhaustive — up to 500 resolved positions and 5,000 activity events per trader, enough for a ranking signal, not a full audit for a very high-frequency trader.

Two fields are honest gaps, left None rather than guessed: category_mix_json and median_market_liquidity both need a per-market gamma-api lookup that isn't built — this is why the "Category mix" section is usually empty on a trader's page, and why decide.py (below) can't enforce a mandate's category/liquidity rules yet either.

polyprinter/scout/shrinkage.py— why the ranking isn't just "biggest ROI wins"

Two small, pure functions implementing the shrinkage correction.

shrink(n, roi, pop_mean, k=30)
The formula: (n·roi + k·pop_mean) / (n + k). A trader is treated as if they'd also played ~30 "average" trades on top of their real ones — a 6-trade sample gets pulled hard toward the middle, a 400-trade sample barely moves.
population_mean(rois)
Average raw ROI across the current batch of candidates — recomputed every scan, not a fixed constant, so shrinkage always compares against the population it's actually part of.
polyprinter/scout/run.py— the entrypoint that ties discover → dossier → shrink together
run_once(conn, log)
One full scan: discover candidates → compute a dossier for each (one bad candidate is logged and skipped, never kills the run) → compute the population mean → shrink every trader's ROI against it → insert one trader_snapshots row per trader (append-only, never an UPDATE — a trader's trajectory over time is itself a signal).
main()
CLI entrypoint. --loop repeats run_once every --interval-seconds (default 24h); writes a heartbeat before and after every attempt, even on failure, so a dead Scout is visibly distinguishable from a quiet one.

Mandates — the LLM judgment layer

Right after Scout writes each watched trader's snapshot, it asks an LLM (over OpenRouter — user's choice: deepseek/deepseek-v4-flash-0731) to read that dossier and issue a mandate: FOLLOW, WATCH, or SKIP, with a confidence level, optional sizing/price limits, and prose reasoning. There's no separate "mandate service" — Scout owns the mandates table, so this runs as a step inside Scout's own daily cycle, only for the traders Mirror actually watches (not the full ~200-candidate discovery pool — a trader ranked #150 will never be mirrored, so a mandate for them is spend with no purpose).

polyprinter/mandate/trigger.py— don't ask the LLM about a dossier that hasn't changed
should_reevaluate(conn, address, latest_snapshot)
Compares the latest snapshot against whatever snapshot the trader's current mandate was issued from. Triggers a new LLM call if either: 5+ newly resolved positions since then, or shrunk ROI / hold-to-resolution rate moved more than 15% relative. Otherwise skips — daily re-analysis of an unchanged dossier is exactly the budget burn this exists to prevent.
polyprinter/mandate/prompt.py— dossier → a prompt a model with no prior context can actually use
build_prompt(trader, snapshot)
Formats one trader's latest dossier into a prompt that explains every term inline — shrinkage, hold-to-resolution rate, profit concentration, entry price spread, sizing pattern — in the same plain language as the Definitions tab, then asks for a verdict grounded in those actual numbers.

Found live: a terse, jargon-only version of this prompt ("22% shrunk ROI, 400 trades...") got misread by the model as confusing rather than informative. The real prompt defines every term before asking anything.

polyprinter/mandate/schema.py— what the model is allowed to say, checked twice

Two independent representations of the same shape: a hand-written JSON Schema constrains what the model can even generate (via OpenRouter's strict structured-output mode); a pydantic MandateOutput model is a second, independent check on our side. Both matter — a model can emit schema-valid JSON that's still semantically wrong (e.g. a price floor above its own ceiling), which only the pydantic validator catches.

polyprinter/mandate/issue.py— trigger check → budget check → call → validate → persist
maybe_issue_mandate(conn, log, trader, snapshot, client, daily_budget_usd)
The whole sequence, in order: skip if trigger.should_reevaluate says no; skip if today's total LLM spend (summed from llm_calls) has hit the daily cap; otherwise build the prompt, call the LLM, validate the response, and write it to mandates — superseding whatever mandate was previously active for that trader. Every attempt is logged to llm_calls in full (invariant 4), valid or not. Never raises — one trader's LLM failure logs and moves on, same discipline as a failed dossier fetch.
today_llm_spend_usd(conn)
Sums llm_calls.cost_usd for today — the hard budget cap (config.yaml's mandate.daily_budget_usd, currently $1/day) checks against this before every call, not after.

Two real bugs found via live runs, not fixture tests: (1) the configured model is a reasoning model whose reasoning tokens are emitted before the actual answer and count against the token budget — a short test prompt passed fine, then a real dossier prompt truncated mid-JSON in production. Fixed with a low reasoning-effort setting plus a generous token ceiling. (2) One trader's mandate call used to crash Scout's entire run, discarding an already-good snapshot batch — the mandate loop lacked the same "one bad item logs and continues" discipline the dossier loop already had. Both fixed the same day they were found.

polyprinter/sources/openrouter.py— the LLM call itself
complete_json(prompt, json_schema, schema_name, max_tokens)
One chat completion against OpenRouter, constrained to the given schema, with retry on 429/5xx/408 (same sources/retry.py every other client uses) and the raw response persisted before anything parses it — same structural rule as the Polymarket clients.

Mirror — watches traders and decides what to do

Runs every 60 seconds by default. Each cycle: pick which traders to watch, poll each one for anything new, and for every trade found, decide TAKE, SKIP, or MIRROR_EXIT — and write that decision down, always, no exceptions.

polyprinter/mirror/watch_poll.py— the main loop: pick, poll, record, decide
select_watchlist(conn, n=20)
Top 20 traders by their latest shrunk ROI snapshot — re-picked fresh every single cycle from whatever Scout currently has. No fixed list to maintain by hand; a trader falling out of the top 20 simply stops being watched next cycle.
poll_trader(conn, client, log, address)
For one trader: works out where we left off (see _watch_start_epoch below), fetches their activity since then, and for every genuinely new TRADE entry — inserts an observed_trades row, calls decide(), and inserts exactly one decisions row. REDEEM/CONVERSION entries are logged but skipped — neither is a buy/sell we can mirror.
_watch_start_epoch(conn, address)
The moment we started watching this trader, persisted as an event the first time we see them. Deliberately not recomputed as "now" every cycle — a trader with zero trades so far would otherwise have their polling window silently reset every single time, permanently missing anything that happened between cycles. Found and fixed this exact bug while building it.
_already_recorded / _next_log_index(...)
Idempotency. Poll windows deliberately overlap (safer than risking a gap), so the same trade often gets fetched twice — _already_recorded recognizes an exact repeat (same tx, same address, same token, same side/shares/price) and skips it rather than double-recording.
run_once(conn, log, mode, mirror_config)
One cycle across the whole watchlist. One bad trader (a request error, a malformed response) is logged and skipped, never kills the cycle for everyone else.
polyprinter/mirror/position_model.py— how big was their position *before* this trade?

Two small, pure (no database, no network) functions — the math behind "they sold 40% of their holding, so we sell 40% of ours."

running_position(events)
Replays a trader's BUY/SELL history for one token in order — BUY adds shares, SELL subtracts — and returns what they're left holding.
fraction_of(position_before, shares_moved)
What fraction of their pre-trade position this trade represents, clamped to [0, 1]. Returns None if we don't actually know their prior position — e.g. we only started watching them after they'd already built it — rather than reporting a made-up fraction.
polyprinter/mirror/decide.py— the actual TAKE / SKIP / MIRROR_EXIT logic

Every observed trade goes through exactly one of two paths, depending on whether it's them buying or selling.

Entry (they BUY) — checked in this order, first failure wins:

1NO_MANDATENo mandate has ever been issued for this trader yet — either they haven't reached the watchlist's mandate pass, or Scout hasn't run since they joined it.
2MANDATE_EXPIREDA mandate exists but its expires_at has passed.
3MANDATE_NOT_FOLLOWThe active mandate's verdict is WATCH or SKIP, not FOLLOW. This is what most decisions hit right now — every real mandate issued so far has come back SKIP.
4PRICE_BANDEntry price falls outside the mandate's min/max entry-price band.
5NO_CAPITALNot enough of the paper bankroll left free (sizing.py's available_capital_usd).
6PORTFOLIO_CAPWould push total open exposure past the portfolio-wide cap.
7CORRELATION_CAPWould push exposure to this one market, across every followed trader, past its own cap — ten traders all in one market is concentration, not diversification.
8TAKEEvery check passed. Size = the trade's requested $ amount, clamped to the mandate's own per-trade ceiling if it has one.

Exit (they SELL) — a completely different, shorter path:

1NO_MATCHING_POSITIONWe hold nothing of ours in this token — almost always because we never took the entry (no mandate existed then either).
2MIRROR_EXITWe do hold a position. Sell the same fraction they just sold (via position_model.fraction_of). Notably: this path never checks a mandate at all — an expired or withdrawn mandate still lets us get out of a position it once authorised. Falls back to a full exit if the fraction can't be computed, since holding an unknown-sized remainder is worse than closing early.
decide(conn, trade, mode, mirror_config)
Dispatches to decide_entry or decide_exit based on the trade's side. This is the one function watch_poll.py actually calls.

Not implemented, on purpose: a mandate's category-allow/block and minimum-liquidity rules. Neither a trade's category nor its market's liquidity is available on an observed trade today — the identical gap dossier.py already has. Faking a match would be worse than not checking it.

polyprinter/mirror/sizing.py— the three caps a TAKE has to clear
per_trade_cap(requested_usd, mandate_max_usd)
The smaller of what we'd size the trade at and the mandate's own per-trade ceiling.
portfolio_exposure_usd / market_exposure_usd(conn, ...)
Sums the cost basis of every OPEN/PARTIAL position we hold — overall, or within one specific market across every trader we follow.
check_portfolio_cap / check_correlation_cap(conn, ..., cap_usd)
True if adding this trade keeps us under the relevant cap. Both configured in config.yaml (mirror.portfolio_exposure_cap_usd, mirror.correlation_cap_usd).
available_capital_usd(conn, mode, bankroll_usd)
Paper bankroll minus what's already committed to open positions — capital locked in a position isn't free for the next trade.
polyprinter/mirror/fills.py— fill simulation
walk_book(levels, size_usd, fee_bps=200)
Given an order book, spends our size level-by-level (crossing the spread), applies a taker fee, and returns the real average price we'd have paid — never assumes we got their exact price. Still not wired to anything: there's no verified-live Polymarket order-book endpoint in this project, so nothing feeds it a real book yet. Built and unit-tested, ready the moment one exists.
approximate_fill(price, size_usd, fee_bps=200)
What actually runs today, via execute.py below. A deliberately optimistic stand-in for walk_book — assumes we fill at the trader's own observed price, zero slippage, the same real fee. Understates copy tax rather than overstates it (the safe direction to be wrong in for a viability measurement), and swaps out for walk_book with no other code changes once a real book exists.
polyprinter/mirror/execute.py— turns a TAKE/MIRROR_EXIT verdict into a real position
open_position(conn, decision_id, trade, size_usd, mode)
decide.py only computes what SHOULD happen; this is what actually opens a positions row. Found missing by code review 2026-08-08, before any FOLLOW mandate had fired — without it, a real TAKE would have logged a decision with nothing behind it.
record_exit(conn, decision_id, position, trade, fraction)
One position_exits row per partial exit (FR-13) — a position goes PARTIAL, not CLOSED, until fraction has taken shares_open all the way to zero.

Mirror — event detection (Phase 4, in progress)

A second, independent way of seeing the same trades — watching the Polygon blockchain directly instead of polling Polymarket's HTTP API — run alongside polling, not in place of it, until proven to agree.

polyprinter/sources/chain.py— reads OrderFilled events straight off Polygon

Every trade on Polymarket settles through the CTF Exchange contract, which emits an OrderFilled event per fill. Verified live 2026-08-08, not inferred: decoded two real transactions (one BUY, one SELL) and matched every field — trader address, token, side, price, size — against data-api's own record of the same trade. One finding worth naming: the contract emits two OrderFilled events per match, and in one of them the "taker" field is the exchange contract itself, not a second person — the trader's own address only ever shows up as "maker", regardless of which side of the match they were on. Get that backwards and you'd misattribute or silently drop trades.

polyprinter/mirror/watch_events.py— detects, but does not decide

Runs every Mirror cycle alongside polling, watching the same watchlist. Deliberately does not call decide()/execute() — running both paths live would double-book the paper portfolio, since polling's log_index is made up (just "the Nth entry we've seen for this tx") while the chain's is the real on-chain value, so the two would almost never collide on the database's own duplicate-safety check and both would happily act on the same real trade twice. Instead every detected fill is just logged, for comparison.

polyprinter/mirror/diff_report.py— is the chain seeing what polling sees?

Compares what the chain watcher detected against what polling actually recorded, over the same time window. This is Phase 4's exit criterion made checkable: PRD §7 requires diffs to run clean for 72 hours before polling is ever retired as the thing that actually opens and closes positions. Right now, live: every chain-detected fill has matched a polling-recorded one exactly.

polyprinter/mirror/run.py— the entrypoint

Same shape as Scout's entrypoint on purpose. main() loads mirror: config, then loops watch_poll.run_once every poll_interval_seconds (default 60s), heartbeating before and after every cycle — then, if POLYGON_RPC_URL is configured, runs watch_events.run_once as a second step in the same tick. Missing the RPC URL just disables the chain watcher (logged, not fatal) — same opt-in-by-env-presence pattern Phase 3's mandate issuance already uses.

Walkthrough: how one real decision gets made

Concretely, end to end, for one trade:

1select_watchlist picks the top 20 traders by shrunk ROI. Say trader 0xabc... is #7.
2poll_trader asks Polymarket for 0xabc's activity since we last checked. It comes back with one new TRADE: BUY 40 shares at 55¢ in some market.
3running_position replays 0xabc's prior trades in that same token to work out what they held right before this one.
4An observed_trades row is inserted — the permanent record that this trade happened and when we saw it.
5decide() sees it's a BUY, calls decide_entry. It looks up 0xabc's active mandate. If Scout hasn't evaluated them yet, that's SKIP / NO_MANDATE. If it has (the common case now), the mandate's own verdict gets checked — and since every real mandate issued so far has come back SKIP, this almost always ends as SKIP / MANDATE_NOT_FOLLOW instead, without ever reaching the price-band or sizing checks.
6A decisions row is inserted, linked to that exact observed_trades row, with the reason recorded in plain text.
7The next time you load /decisions, that row is right there — trader, verdict, reason, latency — because the dashboard reads the same database file, live, on every request.

Dashboard — reads the database, writes nothing else

polyprinter/dashboard/server.py— every route, and the helpers behind the busier pages

Every route below does the same thing at heart: query the database, hand rows to a template. No route ever calls Scout or Mirror — if a page looks stale, it's because the underlying data hasn't changed yet, not because the dashboard is behind.

GET / (now)
System-wide snapshot: heartbeats, copy tax headline, last event, trader/snapshot/decision counts.
GET /traders
Every trader's latest snapshot, ranked by shrunk ROI.
GET /traders/<address>
One trader's full dossier, sparkline history, P&L by market, and recent trades.
GET /decisions
The 200 most recent decisions, joined against the trade that triggered each one.
GET /calibration, /us-vs-them
Intentionally empty until Phase 5 (Learner) and Phase 2's outcomes data exist — see each page's own explanation.

_sparkline(snapshots, field, kind)
Turns a metric's snapshot history into inline-SVG polyline points for the little trend charts on a trader's page.
_recent_trades / _pnl_by_market(conn, address)
Both read Scout's already-archived raw API responses (raw_responses) rather than making a new network call — individual trade history and per-market P&L, straight from data Scout already fetched.

The database — one file, six rules everyone follows

SQLite, WAL mode, at data/polyprinter.db. Every table below has exactly one service allowed to write it.

TableOwnerWhat it holds
tradersScoutEvery address ever discovered, and how.
trader_snapshotsScoutOne append-only dossier per scan — a trader's full metric history over time.
mandatesScout (Phase 3)LLM-issued FOLLOW/WATCH/SKIP verdicts, one per trader Mirror watches, re-issued when the dossier materially changes.
observed_tradesMirrorEvery trade Mirror has ever seen a watched trader make.
decisionsMirrorExactly one row per observed_trades row — TAKE, SKIP, or MIRROR_EXIT, with a reason.
positions / position_exitsMirrorOur own paper positions, and each partial exit against them. Empty today — nothing has been TAKEn yet.
outcomesPhase 5 (Learner, none yet)Resolved P&L and copy tax per position. Empty today.
heartbeatsevery serviceOne row per service, upserted on every tick — "still alive" vs. "silently dead."
eventsevery serviceStructured, queryable log — every Logger.info/error call lands here too, not just in a log file.
raw_responsesevery serviceEvery external API call's raw body, before anything parses it — the audit trail this whole system is built on.

The six invariants (docs/SCHEMA.md), in plain language:

1Every observed trade gets a decision. No trade is ever silently dropped — if Mirror saw it, it's in decisions, even as a SKIP.
2Exiting a position never waits on a mandate. If our mandate to follow someone expires while we're still holding their trade, we can still get out.
3A trader's snapshot history is never edited, only added to — the trajectory itself is signal.
4Every LLM call's full prompt and response get stored, not truncated — the only real audit trail for "why did it say that."
5One writer per table family. The dashboard never writes trading data, ever.
6Every decision and position is tagged paper/live/shadow, so the ledgers can never accidentally mix in a query.

What's real vs. what's still a documented gap

Live and real: trader discovery & scoring (Scout), shrinkage-adjusted ranking, real-time trade detection & decision-writing (Mirror), position/exit bookkeeping (execute.py) with an approximate fill model, all of it against live Polymarket data, all of it verified by 94 passing tests plus real end-to-end runs.
Live and real, added Phase 3: LLM mandate issuance against real dossiers, over OpenRouter, with full prompt/response logging (invariant 4) and a hard daily spend cap — real judgment, real reasoning grounded in real numbers, verified against live runs (including two bugs found and fixed the same day: a reasoning-model token budget pitfall, and a crash-the-whole-batch bug in the mandate loop).
Waiting on an actual FOLLOW verdict: every entry decision still resolves to SKIP in practice — not because the mechanism is missing, but because every real mandate issued so far genuinely came back SKIP. No position has actually opened yet as a result (though the machinery that would is live and tested). A real order-book fill model and category/liquidity mandate rules both stay unbuilt regardless (need endpoints that either aren't verified live or aren't built).
In progress, Phase 4: on-chain event detection (chain.py/watch_events.py) runs live alongside polling, watching the same traders directly on Polygon — but it only logs what it sees, it doesn't drive any decision yet. diff_report.py measures agreement against polling; the exit criterion (PRD §7) is 72 hours clean before polling is ever retired as the thing that actually opens/closes positions.
Not started: Phase 5 (Learner, calibration, shadow benchmark), Phase 6 (live trading).
